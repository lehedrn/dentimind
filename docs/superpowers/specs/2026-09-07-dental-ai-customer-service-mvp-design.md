# 口腔医院AI客服系统 — MVP设计文档

> 日期：2026-09-07
> 状态：待审批
> 目标：4周内搭建可演示的AI客服原型，覆盖文本客服、AI外呼、AI接听三个场景

---

## 1. 背景与目标

### 1.1 客户背景

- 口腔医院连锁机构，80+门店，80名地推市场人员
- 地推月收入240-300万元
- 对SEO/GEO等慢效方式不感兴趣，希望快速看到效果

### 1.2 当前阶段

已完成初步沟通，客户有明确兴趣。需要一个可运行的原型推进合同签署。

### 1.3 MVP目标

- 三个场景均可演示：文本客服、AI外呼、AI接听
- 每个场景可以是简化版，但必须是真实可用的系统
- 4周内完成，越快越好
- 一个人开发，借助AI和开源项目

## 2. 系统架构

### 2.1 四层架构

```
┌─────────────────────────────────────────────────┐
│              用户触点层（Channels）                │
│  ┌───────────┐  ┌───────────┐  ┌──────────────┐ │
│  │ 网页/企微  │  │ 外呼电话  │  │  呼入电话     │ │
│  │ (文本通道) │  │ (AI主叫)  │  │ (AI接听)     │ │
│  └─────┬─────┘  └─────┬─────┘  └──────┬───────┘ │
└────────┼──────────────┼───────────────┼─────────┘
         │              │               │
         ▼              ▼               ▼
┌─────────────────────────────────────────────────┐
│              对话引擎层（Brain）                   │
│  ┌──────────────────────────────────────────┐   │
│  │            Dify (LLMOps平台)              │   │
│  │  - 对话流程编排                            │   │
│  │  - 知识库管理（口腔FAQ）                    │   │
│  │  - 文本通道直接响应                        │   │
│  │  - 对外暴露API供语音通道调用                │   │
│  └──────────────────────────────────────────┘   │
└─────────────────────────────────────────────────┘
         ▲               │
         │               ▼
┌─────────────────────────────────────────────────┐
│              语音处理层（Voice）                   │
│  ┌──────────────────────────────────────────┐   │
│  │         Vocode (语音AI框架)                │   │
│  │  - 语音合成(TTS) / 语音识别(ASR)           │   │
│  │  - 通话状态管理                            │   │
│  │  - 调用Dify API获取AI回复                  │   │
│  └──────────────────────────────────────────┘   │
└─────────────────────────────────────────────────┘
         ▲
         │
┌─────────────────────────────────────────────────┐
│              通信基础设施层（Telephony）            │
│  ┌──────────────────────────────────────────┐   │
│  │   云通信API（阿里云语音/腾讯云呼叫中心）     │   │
│  │   或 Vocode内置的Twilio/SIP集成            │   │
│  └──────────────────────────────────────────┘   │
└─────────────────────────────────────────────────┘
```

### 2.2 核心设计原则

1. **知识库统一**：三个通道共享同一套口腔FAQ知识库，在Dify中维护
2. **语音与对话分离**：Vocode只负责"听和说"，"想"的部分交给Dify
3. **渐进式构建**：先文本（最快见效）→ 再语音 → 最后电话集成
4. **每周可演示**：每个里程碑都有可展示的成果，最差情况也能拿文本+模拟语音去见客户

## 3. 技术选型

### 3.1 Dify（对话引擎）

| 项目 | 选择 | 理由 |
|---|---|---|
| 部署方式 | Docker Compose 本地部署 | 开源免费，数据可控，演示时断网也能跑 |
| LLM | 云端API（DeepSeek / 通义千问 / 智谱GLM） | 无需GPU服务器，按量付费成本低 |
| 知识库 | Dify内置RAG | 上传口腔FAQ文档即可，无需额外向量库 |
| 文本通道 | Dify内置Web聊天窗口 + API | 演示时直接用Dify生成的网页嵌入 |

### 3.2 Vocode（语音通道）

| 项目 | 选择 | 理由 |
|---|---|---|
| ASR（语音识别） | 阿里云智能语音 / 讯飞 | 中文识别准确率高，有免费额度 |
| TTS（语音合成） | 阿里云语音合成 / 讯飞 | 中文自然度好 |
| 通话管理 | Vocode核心框架 | 开源，处理通话生命周期 |
| 外呼触发 | Vocode API + 简单Web界面 | 输入号码→点击拨打→AI对话 |

### 3.3 电话线路（最小成本方案）

| 方案 | 成本 | 周期 | 说明 |
|---|---|---|---|
| **A: 云通信试用** | 免费/极低 | 1-3天 | 阿里云语音通知/腾讯云呼叫中心都有试用额度，足够演示 |
| **B: SIP软电话** | 免费 | 即时 | 用Zoeye/微会等SIP客户端，电脑接耳麦演示，不依赖真实电话线路 |

**策略**：方案B兜底（保证一定有东西能展示），同时申请方案A的试用（效果更好）。

### 3.4 知识库内容

初期不需要找客户要资料，直接构建：

- 从口腔连锁医院官网爬取：项目介绍、常见项目价格、预约流程、门店地址
- LLM辅助生成：常见问答对（洗牙疼不疼、种植牙流程、儿童补牙注意事项等）
- 目标：**50-80条高质量FAQ**，覆盖80%的常见咨询

## 4. 数据流设计

### 4.1 场景1：文本客服

```
用户打字 → 网页聊天窗口 → Dify直接处理 → 知识库检索+LLM生成 → 文字回复
```

### 4.2 场景2：AI外呼

```
点击拨打 → Vocode发起通话 → 云通信/SIP拨出 → 用户接听说话
→ ASR转文字 → Vocode调用Dify API → 拿到回复 → TTS语音播报 → 循环
```

### 4.3 场景3：AI接听

```
用户拨入 → 云通信webhook → Vocode接听 → ASR转文字
→ Vocode调用Dify API → 拿到回复 → TTS语音播报 → 循环
```

## 5. 执行计划

### 5.1 前置动作（Day 1 立即启动，与主线并行）

这些动作有等待周期或无依赖，应尽早启动：

| 动作 | 耗时 | 说明 |
|---|---|---|
| 爬取口腔FAQ + LLM生成问答对 | Day 1-2 | 不等系统部署，纯内容工作 |
| 提交阿里云语音服务试用申请 | Day 1 | 有审核周期，1-3天 |
| 提交ASR/TTS服务开通 | Day 1 | 实名认证+开通服务+获取Key |
| 注册讯飞开放平台（备选） | Day 1 | 作为ASR/TTS的备选方案 |

### 5.2 主线里程碑

#### Week 1：文本通道（Day 1-7）

| 天 | 任务 | 交付物 |
|---|---|---|
| Day 1-2 | Docker部署Dify（前置线同步准备知识库内容） | Dify可访问 |
| Day 3 | 导入知识库（内容已在前置线备好） | 知识库就绪 |
| Day 4-5 | 配置对话流程（欢迎语→意图识别→知识库检索→回复），调试Prompt | 对话效果可用 |
| Day 6-7 | 生成网页聊天窗口，本地演示文本客服 | **里程碑1：文本客服Demo可演示** |

**检验标准**：打开网页，输入"我想洗牙，多少钱？"，AI能准确回答并引导预约。

#### Week 2：语音通道（Day 8-14）

| 天 | 任务 | 交付物 |
|---|---|---|
| Day 8-9 | 部署Vocode，配置ASR（Key已在前置线拿到） | 语音能转文字 |
| Day 10-11 | 配置TTS，调通语音合成 | 文字能转语音播放 |
| Day 12-13 | Vocode对接Dify API：语音输入→调Dify→拿回复→语音输出 | 语音对话链路跑通 |
| Day 14 | 优化对话体验（打断处理、静默检测、语速调整） | **里程碑2：语音AI对话可演示** |

**检验标准**：对着麦克风说话，AI能听懂、思考、用语音回答口腔相关问题。

#### Week 3：电话集成（Day 15-21）

| 天 | 任务 | 交付物 |
|---|---|---|
| Day 15-16 | 确认云通信试用已审批通过（前置线已申请） | 拿到测试号码/额度 |
| Day 17-18 | 对接外呼：触发拨打→Vocode处理通话 | 能主动打电话 |
| Day 19-20 | 对接接听：来电webhook→Vocode接听→AI应答 | 能接电话 |
| Day 21 | SIP软电话兜底方案验证 | **里程碑3：三通道全部可演示** |

**检验标准**：用手机拨打测试号码，AI接听并回答；从系统点击外呼，电话打通后AI对话。

#### Week 4：演示打磨（Day 22-28）

| 天 | 任务 | 交付物 |
|---|---|---|
| Day 22-23 | 编写演示话术脚本（模拟真实客户咨询场景） | 3-5个标准演示场景 |
| Day 24-25 | 全流程联调，修复问题，优化响应速度 | 系统稳定 |
| Day 26-27 | 准备演示PPT + 备选方案（网络/电话故障怎么办） | 演示材料齐全 |
| Day 28 | 内部演练2-3遍 | **里程碑4：可以面对客户演示** |

### 5.3 压缩可能性

如果前置动作顺利（知识库内容ready、云通信审批通过、ASR/TTS Key拿到），整体计划可从4周压缩到**3周**，剩余1周作为buffer应对意外。

## 6. 风险与备选方案

| 风险 | 影响 | 备选方案 |
|---|---|---|
| 电话线路申请不下来 | 无法真实拨打电话 | SIP软电话演示，效果一样，只是不走真实电话网 |
| Vocode中文适配有问题 | 语音通道无法跑通 | 降级为：纯Python脚本 + 讯飞API直接对接，不用Vocode框架 |
| 知识库效果不好 | AI回答不准确 | 缩小范围，只准备20条高频FAQ，保证核心场景完美 |
| Dify部署环境问题 | 文本通道无法使用 | 使用Dify云服务版（ dify.ai ），跳过本地部署 |
| LLM API响应慢 | 对话体验差 | 换用更快的模型（如DeepSeek），或增加流式输出 |

## 7. 成功标准

MVP完成后，以下场景必须能演示：

1. **文本客服**：用户在网页输入口腔相关问题，AI在3秒内准确回答
2. **AI外呼**：从系统输入电话号码，点击拨打，AI在电话中与客户对话
3. **AI接听**：客户拨打指定号码，AI自动接听并回答咨询
4. **知识库**：三个通道共享同一套知识库，回答一致
5. **演示流畅**：能在客户现场完整演示三个场景，不出现明显卡顿或错误
